# 普遍原則・数値基準・プラットフォーム規約（詳細）

SKILL.md本体の基準表で足りない場合、または「なぜこの基準か」を説明する必要がある場合に読む。

## 認知の法則（詳細）

| 法則 | 内容 | チェック観点 |
|---|---|---|
| ヤコブの法則 | ユーザーは他サイトで大半の時間を過ごしており、既知の型を期待する | ロゴは左上か、カートは右上か、ナビは想定される場所にあるか。奇抜なナビは離脱要因になりうる |
| ヒックの法則 | 選択肢が増えるほど決定が遅れる | 主要CTAは1画面1つに絞れているか。メニュー項目は7以内が目安か |
| フィッツの法則 | 標的までの距離と大きさで到達時間が決まる | 重要ボタンは大きく、親指の届く画面下部（モバイル）に配置されているか |
| ミラーの法則 | 短期記憶は4±1チャンク | フォームはグルーピングされているか。電話番号等は分割されているか |
| ドハティ閾値 | 応答400ms以内で「対話」の感覚が保たれる | スケルトンUI・楽観的更新で体感速度を稼いでいるか |
| 美的ユーザビリティ効果 | 美しいUIは使いやすいと知覚される（ただし実際の欠陥を隠す危険もある） | 見た目の良さで機能的な欠陥を誤魔化していないか |
| ゲシュタルト（近接・類似・閉合） | 近いものは同じ仲間に見える | 余白は罫線より強いグルーピング手段になっているか。ラベルと入力欄の距離＜次項目との距離になっているか |

ニールセンの10ヒューリスティックスのうち特に効くもの：
- **システム状態の可視化**：ローディング・処理中・エラーの状態がユーザーに常に見えているか
- **ユーザーコントロールと自由**：Undo/キャンセル・戻る動線があるか
- **エラー防止＞エラーメッセージ**：そもそも間違えられないUIになっているか（エラーメッセージの丁寧さより優先度が高い）

## 数値基準の詳細と出典根拠

### スペーシング
- 8ptグリッドが事実上の業界標準（Apple HIGも一貫性とスケーラビリティのために8ポイントグリッドを推奨）。細かい調整は4pt刻みまで。
- 余白は 4, 8, 12, 16, 24, 32, 48, 64 のスケールに固定し、中間値（例：13px, 27px）を作らない。

### タイポグラフィ
- 本文最低16px。モバイルで16px未満はiOS Safariで入力時に自動ズームが発生する実害がある。
- 行長：欧文45〜75文字、日本語35〜45文字（半角80文字目安）。
- 行間：本文1.5〜1.75（欧文）、日本語は1.7〜1.8を推奨（詳細はjapan-specific.md）。見出しは1.1〜1.3。
- 型スケールは1.25倍（Major Third）か1.333倍で組む。サイズ種類は5〜7個まで。

### 色
- 60:30:10（ベース:メイン:アクセント）が基本比率。
- 純黒 #000 / 純白 #FFF は避け、#111〜#1A1A1A、#FAFAFA あたりに寄せる（コントラストが強すぎて目が疲れる）。
- 色だけで情報を伝えない（エラーは赤＋アイコン＋テキストの組み合わせにする）。

### アクセシビリティ（WCAG 2.2 AA基準）
もはや任意ではなく、多くの国・業界で法的要件になりつつある。
- テキストのコントラスト比：通常テキスト4.5:1以上。大きな文字（18pt以上＝約24px以上、または14pt＝約18.5px以上の太字）は3:1以上。
- UIコンポーネント（ボタン、フォームコントロール、アイコンボタン、グラフ内操作要素）・グラフィカルオブジェクト（アイコン、インフォグラフィック、グラフの色付き領域）も、前景/背景で3:1以上必要。
- タップ領域：WCAG 2.2の達成基準2.5.8では最低24×24px。ただしタッチデバイスでの実運用を考慮すると44×44px以上を最低基準にするのが安全（iOSは44pt、Androidは48dpが公式ガイドライン）。
- キーボードフォーカスリングを`outline: none`で消さない。`:focus-visible`で代替スタイルを用意する場合も、視認性は落とさない。
- `prefers-reduced-motion: reduce` に対応し、アニメーションを抑制する分岐を用意する。

### モーション
- UIトランジションは150〜300ms。300ms超は「もっさり」に感じられ、0msは変化に気づけない。
- ease-out（登場）／ease-in（退場）が基本。linearは機械的に見えるため多用しない。

### パフォーマンス（Core Web Vitals）
デザインの良し悪しは体感速度と不可分。以下はGoogleの「Good」閾値（実ユーザーデータの75パーセンタイルで判定）。
- **LCP（Largest Contentful Paint）**：2.5秒未満。最大の画像・テキストブロックの最適化、画像プリロード、クリティカルCSSのインライン化、フォントのpreload + font-display:swap、SSRが主な対策。
- **INP（Interaction to Next Paint）**：200ms未満。2026年現在、最も失敗率が高い指標。長いJavaScriptタスクの分割、インタラクション中のメインスレッドへのyield、DOM複雑度の削減が対策。
- **CLS（Cumulative Layout Shift）**：0.1未満。すべての画像・動画・iframe・広告枠に明示的なwidth/height属性を指定することでほぼ解決する。

注意：Lighthouseのラボスコアが満点でも、実際の中位機種ユーザーの体感が悪ければ意味がない。ラボデータと実ユーザーデータ（CrUX / Search Console）は別物として扱う。

基準値は年単位で見直されるため、日付が重要なレビュー（法対応など）ではWeb検索で最新のWCAG/Core Web Vitals基準を確認すること。

## プラットフォーム規約

### Apple / Liquid Glass（iOS 26〜）
- WWDC25で導入された半透明マテリアル。iOS 26・iPadOS 26・macOS Tahoe 26・watchOS 26・tvOS 26を横断する設計言語。
- 適用範囲が重要：UIの最上位レイヤー（タブバー、ナビゲーションバー、フローティングボタンなど中心的なナビゲーション要素）に使うものであり、コンテンツ領域にガラス質を敷き詰めるのは誤用。
- システム設定（透明度を下げる／コントラストを上げる／視差を減らす）に自動追従する。カスタムでガラス効果を実装する場合、これらのアクセシビリティ設定に追従できているか確認する。
- 標準コンポーネント（SF Symbols含む）を使うのが最も安全。

### Google / Material 3 Expressive（2025〜）
- Material Design 4ではなくMaterial 3の進化形という位置づけ。
- 色・形・サイズ・動き・空間の表現力を拡張。大胆な形と色使いが特徴。
- カラートークンが`surfaceContainerHighest`や`onTertiaryContainer`のように視覚的階層・強調度に応じて拡充されている。セマンティックトークン設計の参考になる。
- 可変フォント軸を活かしたタイポグラフィスケールが採用されている。

両陣営とも向かっている方向は同じ：「静的なスタイル指定」から「文脈に適応するトークン＋マテリアル」への移行。デザインシステムを新規に組むなら、この方向性（セマンティックトークン、状態適応）を意識する。

## デザインシステムの鉄則（再掲・チェック用）

1. セマンティック命名：`blue-500`ではなく`color-action-primary`。ダークモード対応が一撃で終わる。
2. トークン3層：Primitive（#0A84FF）→ Semantic（action-primary）→ Component（button-bg）。コンポーネントからPrimitiveを直接参照させない。
3. コンポーネントは8状態（default / hover / focus / active / disabled / loading / error / empty）を持つ。
4. 空・エラー・ローディングを後回しにしない。ここの設計品質がプロダクトの印象を決める。
